# Fork

`custom` is upstream `main` plus the feature and fix branches kept in this fork, merged with `--no-ff`. Each branch also lives on its own, so it can go upstream as a pull request.

## Workflow

- New work: branch from `upstream/main`, merge into `custom` with `git merge --no-ff`.
- Work that needs code only `custom` has: branch from `custom`, and rebase onto `upstream/main` before proposing it.
- Sync upstream: `git merge upstream/main` into `custom`. Never rebase `custom`.
- Keep `git config rerere.enabled true`.
- Format check against upstream, locally: `FORMAT_BASE=upstream/main corepack yarn format:check`. The script defaults to `origin/main`, which is stale in a local clone (beta.82 here), so it checks the wrong set of files. CI sets `FORMAT_BASE` itself.

## Versions and release

Tags are the upstream release tag `custom` is based on plus `.custom.N` (`v3.0.0-beta.82.custom.1` for `v3.0.0-beta.82`; `vX.Y.Z-custom.N` on a stable `vX.Y.Z`). The dot keeps SemVer ordering numeric: the platform only auto-updates the CS2 module to a newer version (`beta.100.custom.1` > `beta.99.custom.1`, and a custom build outranks the upstream release it is based on). Pushing a tag builds `ghcr.io/harmdhast/auto-tournament:<tag>` (and `:custom`) for linux/amd64 (`.github/workflows/custom-image.yml`). The tag is the version baked into the image.

CS2 ships as a signed module in the image's offline snapshot. The workflow signs it with the repository secret `MODULE_SIGNING_KEY` (Ed25519 private key, PEM) when set, and instances need `MODULE_TRUSTED_KEYS=<the public key>`. Without the secret a throwaway key is used and the job summary prints the key to trust.

## Migrations

`custom` keeps every branch migration's id and SQL unchanged. Merging the same branch upstream later is then a no-op on a database that ran `custom`. If upstream ships a branch with different ids or SQL, the database needs a manual reconcile.

The runner refuses a pending migration declared before one already applied, so order is part of the contract: fork-only entries keep their position, and every later migration (upstream's or the fork's) is appended at the end of the list in merge order. Never insert before an existing entry.

Fork-only migrations (`api/src/integrations/cs2/migrations.ts`): the first four right after upstream's `043-recorder-host-identity`, where `custom` first shipped them; later ones at the end of the list, in merge order:

| id                              | branch                       |
| ------------------------------- | ---------------------------- |
| `037-fleet-availability-reason` | feat/fleet-busy-reason       |
| `040-server-failover-use`       | feat/failover-server-opt-out |
| `050-match-runtime-cascade`     | match-delete-orphans         |
| `051-round-backup-sides`        | feat/backup-round-sides      |
| `059-fleet-key-machine-id`      | fix/stability-fleet          |

Their numbers overlap upstream's `037-*`, `040-*`, `050-player-roles`, `051-skin-choices` and `059-integration-highlights` ids (upstream's `059` comes after the fork's in the list); ids are unique strings and the runner applies the list in array order, so only the full id matters.

A `custom` database from any point (before the first upstream sync, between syncs, current) plans cleanly (`tests/api/cs2-migration-order.spec.ts`). Known limitation: a database that ran upstream alone up to `044`..`059-integration-highlights` and then switches to `custom` is refused (the fork entries are declared before applied upstream ones); reconcile it by hand.
